One speaker-bureau platform for 17 roles

Pharmaceutical speaker programs — the paid educational events where a doctor presents to peers — ran on email, spreadsheets and a legacy portal. This is the multi-tenant platform where a rep, a compliance monitor and an accountant work the same program record, and the story of how a 496-story backlog became one shippable release.

Seventeen roles touch a single speaker program, each with its own approval gate. Mapped end to end that came to 496 user stories across 13 workflow areas (counted), all competing for one MVP.

Nobody could say where a program was

A speaker program looks like one event and works like a supply chain. A rep nominates a doctor, a manager approves, compliance checks the engagement, a coordinator books travel, accounting settles the fee against a budget set months earlier. Every handoff used a different tool and a different idea of what "done" meant.

Nobody owned the whole thing, so nobody could say where a program was without asking four people. That is the problem underneath every number on this page — and it is why the work started with a map rather than a screen.

The same program means something different to each of them

I mapped all 17 roles and wrote three personas — a sales rep, an event coordinator, a speaker (counted) — and gave each role an as-is and a to-be flow. Three findings came out of it, and only one of them came from the field.

What discovery found

One record, three meanings

To a rep a program is a request waiting on approval. To compliance it is an audit record. To accounting it is a set of charges against a budget line. Same object, three jobs.

The cost sat in accounting

Reconciliation ran daily, by hand, matching card expense reports against cost items on a report of 77 to 102 columns depending on the tenant (client spec). Something that wide, run that often, is where the money goes.

It ends in a federal filing

Payments to doctors are reported to the federal government, so an approval chain nobody can trace is a legal risk, not a hassle. That is why every role doc carries an access matrix and an audit-trail requirement.

The decision: what not to build first

A 496-story backlog across 17 roles isn't a ranking problem. No ordering of 496 items gives you a release that hangs together. Slice it by role and you ship a rep experience that dead-ends at an approval nobody can give. Slice it by feature and you ship a budget module with no program to attach it to.

Options

A

Role-complete. Finish the rep experience, then the next role. Quick to demo, but every flow stops at a role that doesn't exist yet.

B

Feature-complete. Build each of the 13 workflow areas across all roles. Clean, but nothing works until most of it is done.

C

Spine-first. Take the one flow every role touches — request through approval — and ship it end to end for the roles that own it.

Criteria

Can a real program run in production on day one? Does each release leave a working system or a half-built approval chain? Which order tackles the hardest logic earliest? And can a new tenant start without waiting for all 17 roles?

What I chose

C, spine-first. We tiered the backlog Must-have against Post-MVP along the request spine, and shipped the four roles that own a program from start to approval. Budget came with it rather than after: top-down allocation and bottom-up charges carry the weight of the whole record, and putting them off would have meant rebuilding around them later.

What I killed

Every role that only reads the record: attendee self-service, auditor tooling, the rookie track. The thinnest slices, and the ones a working program can live without. The cost was real — attendees stayed on paper sign-in sheets for a release, and the auditor kept exporting instead of querying.

The map is what made that arguable rather than asserted.

What the release actually contains

Five things, in the order they have to exist. Budget is not last: allocation and charges carry the weight of the whole record, and deferring them would have meant rebuilding around them later.

The argument for option C

Onboarding, nomination and contracting are three whole workflow areas and most of their columns are empty. Build those first and you ship a system nobody can run a program in. Program request is the opposite: an unbroken initiate → approve → approve → confirm chain, with the same feature stack under almost every column.

Compare the two bands

Program request — dense, unbroken
Onboarding, nomination, contracting — sparse

That gap is what made the spine-first call obvious before anyone had to be talked into it.

Ten checks, then a federal filing

Run the report, run it again by month, select a program, check attendee duplication against the speaker cap, check identifiers and signatures, check receipts, check cost items, mark QA verified per payment item, mark final verification, pull to the payment aggregator, file the Sunshine Report. Ten manual steps between an event and a government submission, and the chain runs every day.

Each one is a place a program can quietly fail an audit. That is what turns "the tooling is old" into a business case, and it is the single most persuasive artifact in the whole source set.

Three things carried the build. Budget runs in two directions at once — top-down from a signed contract through area allocations, and bottom-up from per-event charges — so I specced the state changes in detail, what happens to committed budget versus money actually spent when a program is approved, cancelled or closed, because that is where reconciliation disputes start. The backlog itself ran to 496 stories in As a… I want… so that… form with acceptance criteria (counted), tiered Must-have against Post-MVP and each traced to an epic, with 19 items still open — a working backlog, not a finished document. And rather than draw the riskiest screens we built them: a React prototype of about 21,350 lines over ten weeks (counted), covering program detail, budget and transfer funds, role dashboards and a form builder, each screen exported on its own so a stakeholder could open one page instead of clicking through a demo.

Building it turned up two things the spec had missed. Tracing a program title back to its request form showed coordinators quietly changing event format and setting type between request and approval — a data problem no amount of writing would have caught. And an audit of design tokens found 17 of 18 status tokens had drifted out of sync with the Figma library.

One scope change is worth recording. Transfer funds started as a panel inside the budget screen and ended up a full page: moving money between allocations needs a two-step confirm and a clear before and after, and a panel couldn't show that without hiding the number the user most needed to check. Worth saying plainly, because it shaped everything else — the design deliverable was a coded prototype in the product's own stack, not a Figma file. Design tokens and a git branch were the source of truth, engineering pulled from there and owned auth, and that is why the token drift got caught at all. It showed up as a diff rather than as a surprise in QA.

Specced, handed off, not measured by me

I moved on before a measurement cycle closed, so there is no outcome number here I can stand behind. I would rather say that than imply a win. What exists is a spec, a working prototype and a sequencing argument that the client accepted — which is a real piece of work, and is also not the same thing as a result.

Three measures are what I would have tracked. Program-request cycle time, from submission to confirmed, is the one I would have set a target on, because that is what the spine-first call was really betting on: if approval cycle time didn't move, the whole argument for shipping the request spine before anything else was wrong. Then coordinator hours to run one program end to end, and the exception rate — compliance issues raised after the fact instead of caught in the flow.

What I'd do differently

496 stories, zero baselines. The spec is thorough — as-is and to-be flows for all 17 roles — but thorough isn't proven, and I still can't tell you what the old process cost. A week timing real program requests at the start would have turned the spine-first argument from a diagram into a measurement.
I let the design system drift. Catching 17 of 18 status tokens out of sync was fine. Needing to catch it was the miss — calling code the source of truth on day one would have cost nothing.
I answered "why now" with a standing reason. Compliance risk is true every quarter. I never pinned down what made it urgent that quarter, which is the first thing anyone senior asks about a project this size.

The shape didn't change.
AI just carries more of it now.

Built

Design moved onto the branch

Seventeen of eighteen status tokens drifted out of sync on this project before anyone noticed. The fix was not more diligence. It was moving the design onto the same branch as the code it describes, so a component change and the screen that consumes it arrive in one review and merge once.

Tokens and components are defined once, in code, and the design reads from them
A design change arrives as a diff — reviewable, arguable, revertable
Nothing is ever “ready for dev”, because the branch already runs

The handoff

Four artifacts became one

Before

Four artifacts, four owners, each written from the last one and drifting from it the moment it was.

A specification document
A design file redrawing what the document said
Tickets restating the design in a third vocabulary
Test cases written against whichever of the three was newest

After

One branch carrying the spec, the screens and something that runs. Reviewed once, on the diff.

The spec, beside the code it specifiesAI + Human
The screens, as components rather than pictures of componentsAI + Human
A prototype a client can click throughAI
The review, once, where the change actually is

That is what the loop above buys. Not fewer people and not less thinking — a client could open the thing and disagree with it while the specification was still being written, which is the only kind of disagreement that is cheap to act on.

The gate

Where a human still owns it

Reconciliation on this platform runs ten manual checks, daily, and ends in a filing to the federal government (counted). Speed is not the thing to optimise there.

That is what the toggle is for. On a flow where being wrong is a legal problem rather than a bug, a person owns every decision and the machine owns the labour — and the honest version of this section is that most of the thirteen workflow areas are not that flow, and one of them very much is.
